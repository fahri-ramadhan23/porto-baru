Building a Zero-Dependency, Thread-Safe Background Task Queue in FastAPI with SQLite WAL Mode

Written by Moh Fahri Ramadhan • Portfolio • GitHub

When you're deploying a single-server Python application—such as a media rendering pipeline or a webhook processor—spinning up Redis, Celery, and a separate broker monitor is often unnecessary operational overhead. SQLite is already built into Python's standard library and easily handles thousands of state transitions per second on modern SSDs.

However, if you naively wire sqlite3 into a multi-worker FastAPI service, you will hit two classic failure modes under concurrent load: sqlite3.OperationalError: database is locked and duplicate task execution caused by race conditions between competing workers.

Here is how to build a rock-solid, atomic task queue in FastAPI using only Python's standard sqlite3 module, Write-Ahead Logging (WAL), and BEGIN IMMEDIATE transactions.

1. Why Unlocked SELECT-Then-UPDATE Fails Under Concurrency

A common anti-pattern when polling SQLite for pending jobs looks like this:

# BUGGY: Two concurrent workers will read the exact same row ID!
row = conn.execute("SELECT id FROM job_queue WHERE status = 'pending' LIMIT 1").fetchone()
if row:
    conn.execute("UPDATE job_queue SET status = 'processing' WHERE id = ?", (row["id"],))
    conn.commit()

By default, SQLite defers acquiring a write lock until the UPDATE statement executes. If Worker A and Worker B hit your endpoint in the same millisecond, both execute the SELECT statement concurrently, both receive id = 42, and your background pipeline processes the same customer job twice.

2. Atomic Job Claiming with WAL Mode and BEGIN IMMEDIATE

To eliminate the race condition without external locks, we configure three settings on our SQLite connection:

  • PRAGMA journal_mode=WAL; — Allows concurrent readers while a write transaction is in progress.
  • timeout=30.0 — Tells SQLite to wait up to 30 seconds for a busy lock to clear instead of failing immediately.
  • isolation_level=None (Autocommit) + Explicit BEGIN IMMEDIATE — Acquires a reserved write lock at the very start of the transaction before the SELECT query runs, serializing competing workers cleanly.
import sqlite3
from contextlib import contextmanager
from datetime import datetime, timezone
from fastapi import FastAPI
from pydantic import BaseModel

DB_PATH = "tasks_wal.db"
app = FastAPI()

def init_db() -> None:
    with sqlite3.connect(DB_PATH, timeout=30.0) as conn:
        conn.execute("PRAGMA journal_mode=WAL;")
        conn.execute("PRAGMA synchronous=NORMAL;")
        conn.execute("""
            CREATE TABLE IF NOT EXISTS job_queue (
                id INTEGER PRIMARY KEY AUTOINCREMENT,
                task_name TEXT NOT NULL,
                payload TEXT NOT NULL,
                status TEXT NOT NULL DEFAULT 'pending',
                updated_at TEXT NOT NULL
            )
        """)

@contextmanager
def atomic_db():
    # isolation_level=None lets us manage BEGIN IMMEDIATE / COMMIT explicitly
    conn = sqlite3.connect(DB_PATH, timeout=30.0, isolation_level=None, check_same_thread=False)
    conn.row_factory = sqlite3.Row
    try:
        yield conn
    finally:
        conn.close()

@app.post("/tasks/claim")
def claim_next_job():
    now_iso = datetime.now(timezone.utc).isoformat()
    with atomic_db() as conn:
        conn.execute("BEGIN IMMEDIATE")
        try:
            row = conn.execute(
                "SELECT id, task_name, payload FROM job_queue "
                "WHERE status = 'pending' ORDER BY id ASC LIMIT 1"
            ).fetchone()
            if not row:
                conn.execute("COMMIT")
                return {"claimed": None}

            conn.execute(
                "UPDATE job_queue SET status = 'processing', updated_at = ? WHERE id = ?",
                (now_iso, row["id"]),
            )
            conn.execute("COMMIT")
            return {"claimed": dict(row)}
        except Exception:
            conn.execute("ROLLBACK")
            raise

3. Benchmark Results

With BEGIN IMMEDIATE and WAL mode active, firing 200 concurrent worker requests against 50 queued jobs yields exactly 50 unique claims and 150 clean {"claimed": null} responses—with zero duplicate executions and zero database is locked exceptions.
